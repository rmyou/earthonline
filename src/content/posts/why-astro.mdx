博客首先是内容系统，不应该让作者每次发布文章都先处理一堆基础设施。这个站点选择 Astro，核心原因是它能把内容优先、静态输出和足够的交互能力放在同一个工程里。

## 目录

## 内容优先

文章以 Markdown 和 MDX 文件保存在仓库中。发布一篇文章只需要新增文件、提交并推送，不需要数据库、后台服务或单独的编辑器。

内容集合会校验 Frontmatter，缺少标题、日期或描述时直接让构建失败。这比上线后再发现元数据缺失更可靠。

```yaml
title: 一篇文章
description: 文章摘要
pubDatetime: 2026-09-13T19:00:00+08:00
tags:
  - Astro
draft: false
```

## 静态输出更适合博客

这个博客没有登录、实时协作或用户私有数据，因此没有必要依赖服务端渲染。Astro 在构建阶段生成 HTML、RSS、sitemap 和搜索索引，浏览器得到的是可以直接缓存的静态文件。

内容再多，部署模型也不会变复杂：构建产物输出到 `dist`，Vercel 负责分发和 HTTPS。

> [!TIP]
> 静态站点的边界很清晰：需要用户身份、写入数据库或实时数据时，再引入服务端能力，而不是一开始就为它们买单。

## 搜索也能保持简单

全文搜索由 Pagefind 完成。它在构建后扫描生成的 HTML，建立静态索引，不需要外部搜索服务，也不会把文章内容发送到第三方。

这带来两个直接好处：

- 搜索仍然属于站点本身，隐私和可用性更可控。
- 没有常驻服务，维护成本接近零。

## 部署交给 Vercel

GitHub 是内容和代码的单一事实来源。每次推送到 `main`，Vercel 自动执行构建并发布生产版本；其他分支和 Pull Request 会生成独立预览地址，方便上线前检查。

这套流程的复杂度足够低，也保留了后续扩展空间。真正重要的不是工具本身，而是它能让写作和发布保持可持续。

## 最后的判断

选择 Astro 不是因为它能做出最多的效果，而是因为它默认鼓励我减少不必要的运行时。对于一个以长期写作为目标的博客，这种克制比功能数量更重要。
